# Versioning, compatibility, snapshots and rollback

## What identifies a build

| Identity | Source of truth | Bump when |
|---|---|---|
| Build version (semver) | `SANDBOX/godot/project.godot` `application/config/version` | any release-worthy change (human decision) |
| Git commit | git | automatically |
| Godot engine version | `INFRASTRUCTURE/builds/toolchain.json` | engine upgrade (ADR + approval) |
| Network protocol version | `project.godot` `structure/network/protocol_version` | any change to RPCs, their arguments, auth payloads or event shapes |
| World schema version | `project.godot` `structure/persistence/world_schema_version` | any change to `world.json` structure or meaning |
| Oldest loadable schema | `project.godot` `structure/persistence/min_world_schema_version` | when a migration path is dropped |
| Server image | `structure-server:<version>-<sha7>[-dirty.<UTC>]` | every `structure.py build` (tags are never overwritten) |
| Asset manifest | `COMMON-ASSETS/manifests/assets.json` (sha256 in the build manifest) | regenerated by the pipeline |

`structure.py build` writes all of this into a build manifest that is baked into the image
(`res://build_manifest.json` + image label `org.structure.manifest`). Running servers log it in `server.starting`
and send it to clients in the welcome message. `structure.py versions` and `structure.py builds` display it.

## Compatibility rules

- **Client <-> server**: identical protocol version, otherwise the server rejects the client during authentication
  (`protocol_mismatch`). Different build versions with the same protocol are allowed.
  Check offline: `structure.py compat --client current --server <tag>`.
- **World <-> server**: `min_world_schema_version <= world schema <= world_schema_version`.
  - Newer world than the server supports: the server refuses to start and leaves the file untouched.
  - Older but migratable: the server migrates on load and keeps the original as `world.v<N>.json`.
  - Older than the minimum: refused.
- **Snapshots** obey the same world rule against the build that will load them (`compat --snapshot <env>/<id> --server <tag>`).

## Snapshots

`structure.py snapshot create <env> [--label x]` copies `world.json` into `INFRASTRUCTURE/snapshots/<env>/<UTC>-<label>/`
with `snapshot.json` (world id, seed, schema, revision, progress, source build, sha256). Snapshots are local data
(git-ignored) and are never deleted by tooling.

`structure.py snapshot restore <env> <id> --yes`:
1. refuses while any server (container or native) uses the environment (container state + heartbeat lease);
2. verifies the snapshot's sha256;
3. checks schema compatibility with the target build (`--build <tag|current>`; default: the env's pinned image or the newest build);
4. refuses a different `world_id` unless `--allow-other-world`;
5. snapshots the current world as `pre-restore` (and moves stale `world.json.bak`/`.tmp` into it);
6. atomically replaces `world.json`. `--dry-run` prints the plan without changing anything.

## Rollback

A git checkout of an older commit is **not** a complete rollback: the world may have been saved by a newer schema.
To roll back a server: pick the build (`structure.py builds`), check the world (`compat --snapshot ... --server <old tag>`),
restore a compatible snapshot if needed, then `structure.py env up <env> --image-tag <old tag>`.
Destructive data operations always require `--yes` and take a snapshot first (`env purge`, `snapshot restore`).

## Limitations (phase 0.1)

Local Docker images only (no registry); snapshots are full copies (fine at current world size); no automatic
retention policy; migrations exist as a framework only (schema v1 has no predecessors).
